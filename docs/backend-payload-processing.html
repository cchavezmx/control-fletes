Control de Fletes · Backend

Procesamiento del payload de flotilla

Documento vigente

Instrucciones para que el backend/API procese correctamente la creación y actualización de documentos de Traslado, Flete y Renta enviados desde el frontend de Control de Fletes.

1. Contexto

El frontend centralizó el cálculo de costos en utils/costBreakdown.js. El payload que llega ahora es predecible: campos de conceptos como strings, porcentajes como números, y un objeto cost_breakdown anidado con los importes calculados. El backend debe:

  1. Coercer los campos numéricos del payload a Number antes de persistir.
  2. Guardar el objeto cost_breakdown tal cual llega.
  3. Al generar PDFs o reportes, recalcular el subtotal desde cost_breakdown, no confiar en subtotal_travel legacy.
  4. Respetar la unidad de gasolina para no multiplicar un monto fijo por el recorrido.
Regla de oro: el frontend ya no duplica la lógica. Si el backend recalcula distinto, el PDF y el drawer mostrarán totales diferentes. Ambos deben usar la misma fórmula documentada aquí.

2. Endpoint y formato

El frontend hace POST a: 

POST ${NEXT_PUBLIC_API}/flotilla/insert?type=traslado|flete|renta
Content-Type: application/json

Para actualización:

PUT ${NEXT_PUBLIC_API}/flotilla/update/:id?type=traslado|flete|renta
Content-Type: application/json

4. Cálculo que debe aplicar el backend

Fórmula oficial conceptos = casetas_amount + (operator_rate × operator_days) + (per_diem_rate × per_diem_days) + (gasoline_rate × gasoline_km cuando unit === 'km', sino gasoline_rate) + (unit_rent_amount × unit_rent_qty) subtotal = redondear2(conceptos) utilidad = profit_amount ?? redondear2(subtotal × profit_pct / 100) indirectos = indirect_amount ?? redondear2(subtotal × indirect_pct / 100) base = redondear2(subtotal + utilidad + indirectos) iva = redondear2(base × 0.16) total = redondear2(base + iva)

Donde redondear2(x) = Math.round(x * 100) / 100.

Nota: los campos profit_amount e indirect_amount ya viajan calculados. El backend puede usarlos directamente para evitar drift. Si no viajan (documentos legacy), recalcular desde los porcentajes.

5. Regla crítica: gasolina

El wizard captura gasolina como un monto fijo por defecto. El campo gasoline_unit indica cómo interpretarla:

  • gasoline_unit === 'km' y gasoline_km > 0: importe = gasoline_rate × gasoline_km.
  • Cualquier otro caso (incluyendo fijo, dia o ausente): importe = gasoline_rate. No multiplicar por nada.
Advertencia: si el backend ignora gasoline_unit y siempre hace gasoline_rate × gasoline_km, cuando el wizard envíe un monto fijo de $2,500 con gasoline_km: 1 el resultado será correcto. Pero si un documento legacy tiene gasoline_km: 420 pensando que es recorrido, el importe se disparará a $1,050,000. Respetar la unidad es la única forma segura.

6. Qué persistir

El backend debe persistir al menos:

  • El objeto cost_breakdown completo (campos de desglose + profit_amount + indirect_amount).
  • subtotal_travel como Number.
  • profit_pct e indirect_pct como Number.
  • pre_flight anidado.

Si el backend transforma a un schema propio, debe asegurar que los tipos sean numéricos:

cost_breakdown: {
  casetas_amount: Number(doc.casetas_amount || 0),
  operator_rate: Number(doc.operator_rate || 0),
  operator_days: Number(doc.operator_days || 0),
  // ... etc
}

7. Qué devolver al frontend

En los endpoints de lectura (especialmente GET /flotilla/documentos/:empresaId), devolver cada documento con:

{
  "_id": "...",
  "type": "Renta",
  "folio": 1,
  "subtotal_travel": 38823.68,
  "profit_pct": 8,
  "indirect_pct": 12,
  "cost_breakdown": { /* objeto completo */ },
  "pre_flight": { /* objeto completo */ }
}

El frontend usa cost_breakdown para renderizar el drawer. Si falta, cae a subtotal_travel como fallback, pero sin desglose por concepto.

8. Compatibilidad legacy

Documentos antiguos pueden no tener cost_breakdown. En ese caso:

  1. Usar subtotal_travel como subtotal.
  2. Calcular utilidad e indirectos desde profit_pct / indirect_pct.
  3. No intentar desglosar conceptos.

10. Checklist de QA

  • Crear un documento de renta con todos los conceptos: wizard, drawer y PDF muestran el mismo total.
  • Crear un documento con gasolina fija: el PDF no multiplica por el recorrido.
  • Verificar documentos legacy: el drawer muestra el subtotal aunque no haya desglose.
  • Verificar montos con decimales extraños (ej. $1,000.555): redondeo a 2 decimales sin drift acumulado.
  • Verificar porcentajes 0%: utilidad e indirectos quedan en 0.
Referencia frontend: la implementación de referencia vive en utils/costBreakdown.js. Cualquier discrepancia entre backend y frontend debe resolverse copiando esa fórmula al backend.
